# Custom Aircraft Initialization and Control

Use this procedure when a plugin-heavy aircraft ignores generic autopilot commands, owns its mass/fuel state, or cannot converge with the generic runner alone.

## Requested state is not achieved state

Keep these separate in both code and evidence:

| Layer | Evidence |
|---|---|
| Command request | HTTP activation succeeded with a finite duration. |
| System readiness | Avionics/AP power, plugin-ready, and aircraft-local annunciators. |
| Servo engagement | `servos_on` or the aircraft's equivalent. |
| Achieved mode | Actual lateral/vertical mode datarefs and annunciators. |
| Achieved flight condition | Sampled IAS, altitude, VVI, bank, power, and mass. |

An HTTP 200 or engaged servo is insufficient. After each mode command, wait a bounded time for the actual mode and reject if it never appears. Prefer aircraft-native commands when generic commands are ignored.

Use finite command activations. A 0.2-second press is the proven starting point. When a harness is generated by text replacement or nested adapters, inspect or test the final executable text; changing only the outer wrapper does not prove the generated command body changed.

## Diagnose state snapback and hidden writers

When a command appears inert, sample the relevant state before the command,
immediately afterward, and on subsequent simulator ticks. A state that changes
and then snaps back indicates another writer; it is different from a command
that was rejected.

Audit aircraft and global plugins, external control applications, and Lua
scripts for every writer to the affected dataref. In FlyWithLua, a scalar
`dataref(..., "writable")` binding is continuous ownership: the runtime can
flush its cached variable after command processing even when the script did not
intend a new write. Bind state read-only and use `set()` only during the
explicit, bounded operation that needs to change it. Apply the same ownership
rule to test-only position, attitude, and autopilot helpers.

An isolation comparison is valid only if the suspected component actually
loaded in the non-isolated run. Check `Log.txt`; a control where FlyWithLua or
another implicated plugin failed to load cannot establish that the component
is harmless. Reproduce the user's actual 2D or VR launch path rather than
inferring the mode from a plugin name or feature description.

## Separate button response from guidance capture

NAV and APR may arm and then return to a basic lateral mode when no usable
flight plan, VLOC signal, or course guidance exists. To test full behavior,
provide valid guidance and verify arm, capture, and persistence. If the narrow
question is whether the button reaches the autopilot, pause immediately after
the finite press and sample the armed status before guidance evaluation can
cancel it. Label that result as command/arming evidence, not navigation capture.

## Reset sticky state before every run

Airborne crashes and rejected probes can leave synchronized pitch, altitude, speed, failure, or plugin state behind. While paused:

1. Set every mode reference the upcoming run depends on.
2. Read each value back and enforce a tolerance.
3. Verify plugin/mod active state, avionics/AP power, and aircraft readiness.
4. Reload or restart after implausible state; do not tune around contaminated state.

The SR20 campaign exposed a stale synchronized pitch near -12 degrees that survived a bad run and produced repeated multi-thousand-fpm dives even with servos engaged. This is an example of the failure class, not a universal reset value.

For stateful aircraft, issue a complete `/flight` load for each card. Aircraft initialization may rewrite payload stations after the request returns, so apply the desired masses only after plugin initialization, settle, freeze or pause again if needed, and verify final total mass and CG immediately before the measured phase.

## Controlled convergence

Prefer a native stable AP mode. If none is available, an adapter may adjust one verified reference during a distinct **convergence** phase:

1. Measure the response to small changes using rejected probes.
2. Use bounded increments and hard reference limits.
3. Check servo/mode continuity every iteration.
4. Require altitude/speed/VVI tolerances for multiple consecutive observations.
5. Abort on timeout or implausible response.
6. Stop all controller changes before the official stabilization period begins.

Do not reuse gains across aircraft or simulator versions without re-identifying the response.

For banked setup controllers, verify the sign and units of body roll rate against the displayed Euler bank in a short trace before relying on proportional control. Use bounded authority and keep the achieved pre-measurement bank inside the card's original tolerance; controller difficulty is not a reason to relax acceptance limits.

### SR20 campaign example, not a default

When native ALT capture was unavailable, the accepted cruise harness used AP pitch mode with a pre-stabilization pitch-reference controller. A rejected probe suggested roughly 210 fpm per pitch degree. Every four seconds the controller bounded target VVI to +/-250 fpm, pitch change to +/-0.8 degree, and the reference to -2 through +6 degrees. Convergence required altitude within 8 ft and absolute VVI within 15 fpm for three consecutive checks, with a 45-iteration limit. The controller then stopped, and the 90-second official stabilization period began.

Those values belong only to that TorqueSim SR20/X-Plane campaign. Preserve the pattern, not the gains.

## Correct mass after convergence

Fuel burned during a long controller/acquisition phase can invalidate a tight weight card. Immediately after convergence:

1. Read total mass and the selected adjustable station.
2. Add `target total mass - actual total mass` to that station in matching units.
3. Settle briefly, reread total mass, and iterate within a small bound.
4. Start official stabilization only after correction.
5. Reject if the sampled mean mass misses tolerance.

Do not silently add fuel when fuel quantity is itself a test condition. Use an allowed payload/station adjustment and disclose it.

## FLC speed offsets

Some aircraft synchronize or offset the selected speed at engagement. Engage FLC first, then set the bug. If an exploratory run shows a repeatable difference, command the value needed to obtain the POH actual IAS, record both commanded and achieved IAS, and validate the achieved value. Never compare the selected bug to a POH IAS target as if it were measured airspeed.

## Plugin crash isolation

When X-Plane crashes during load:

1. Inspect `Log.txt` for the named plugin, callback, or threading violation.
2. Confirm whether the failure is global or aircraft-local.
3. With user authorization, move only the implicated plugin file/folder to a named reversible quarantine.
4. Rerun the same load test and preserve both logs.
5. Restore the plugin after testing and confirm restoration.

Do not attribute a global plugin crash to the aircraft mod merely because the aircraft load triggered it.

## Regime-dependent diagnostics

Separate plugin presence/readiness, version, computed factor, and force/application state. A correction plugin may correctly report zero application below its activation threshold even though it is loaded and healthy. Define the expected diagnostic state for each card and reject only a mismatch with that expectation.

## Evidence lineage

- Setup/probe failures: diagnostic evidence only.
- Rejected sample windows: retain raw JSON and explicit reasons.
- Accepted runs: must pass config, state, stability, and no-crash checks.
- Final report: cite exact accepted filenames; keep controller variants and rejected attempts distinguishable.
